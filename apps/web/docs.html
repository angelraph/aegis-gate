Escrow for shielded Zcash

Zcash has no smart contracts, so it has no escrow. When two strangers trade privately, one of them has to pay first and hope. Aegis Gate removes that leap of faith without a custodian and without leaving the shielded pool.

Every deal gets its own escrow: an Ironwood shielded address whose spending authority is a 2-of-3 FROST key (ZIP 312). The buyer, the seller and an arbiter each hold one share. Any two shares together can produce the one signature that moves the money. A single share can't.

Testnet build. Aegis Gate runs on Zcash testnet with test coins (TAZ). Don't send mainnet ZEC to an escrow address.

Quick start

If you're selling

  1. Open a new escrow. Enter what you're selling, the price in ZEC, your terms, and your shielded payout address.
  2. Wait about a minute while the three keys are made.
  3. Send the buyer link to your buyer over Signal, Telegram or any private channel. Bookmark your own link; it's your seller access.
  4. Ship when the deal page shows the payment as confirmed. Approve the release when the buyer confirms delivery.

If you're buying

  1. Open the link the seller sent you. Add a refund address in case the deal is cancelled.
  2. Scan the QR code with your wallet, or copy the escrow address, and pay the exact price.
  3. When the item arrives, press Confirm delivery and release payment.

Getting testnet ZEC

Request free TAZ from the Valar testnet faucet (0.125 TAZ per day). Use a wallet that supports Zcash testnet and the Ironwood pool, and give it a unified address starting with utest1.

Roles and approvals

Each person gets a private link. The link is their identity for this deal: no accounts, no email. A payout runs only when two different people approve the same outcome, and those two are the FROST signers.

SignersOutcomeWhen
Buyer + sellerRelease to the sellerA normal trade
Seller + buyerRefund to the buyerThe seller cancels
Arbiter + sellerRelease to the sellerDispute decided for the seller
Arbiter + buyerRefund to the buyerDispute decided for the buyer
Any one personNothing movesAlways

Disputes

Either the buyer or the seller can open a dispute on a funded deal. The arbiter can sign only after that happens. The arbiter reviews the deal and approves either a release or a refund; the side that agrees approves the same outcome, and the payout runs.

The arbiter can't take the money for themselves: every payout goes to an address the buyer or seller set in advance.

Security model

  • No single point of custody. Spending needs one RedPallas signature that only two of three FROST shares can produce.
  • Verifiable escrow. The escrow address and viewing key are derived from the group key and the deal ID, so every party can recompute them and check they match.
  • Shielded end to end. Funding and payout are Ironwood shielded transactions. Observers see that a transaction happened and its fee, nothing else.
  • Signatures checked before broadcast. Each FROST signature is verified against the spend's randomized key before the transaction is assembled.
Current limitation. In this testnet build, all three FROST signers run inside the Aegis escrow engine, which signs only on two matching approvals from different people. The next release moves each signer into its owner's browser, so the engine never holds more than the arbiter's share. Read the full threat model.

Known risks

  • The arbiter plus one side can decide the outcome. That's what 2-of-3 escrow means; pick an arbiter you're comfortable with.
  • Anyone with your deal link acts as you. Share it only privately.
  • Viewing keys built from a FROST group key aren't quantum-recoverable, so escrows are meant to be short-lived.

Architecture

buyer ─┐                             ┌─ escrow address (Ironwood)
seller ├─ FROST key ceremony ──────► │  spend key = FROST group key
arbiter┘   (encrypted relay)         └─ viewing key = f(group key, deal ID)

payout:
  build + prove PCZT ─► aegis inspect ─► sighash + randomizer per spend
     ─► FROST rounds (2 of 3) ─► aegis apply (verifies each sig) ─► broadcast
  • aegis-core (Rust): escrow derivation, PCZT signing requests, signature application and verification.
  • FROST relay: the Zcash Foundation's frostd; messages are end-to-end encrypted between participants.
  • Escrow engine: deals, private links, two-approval rule, and the payout pipeline.
  • Zcash stack: librustzcash pinned to 9c5705f for NU7, with a port of zcash-devtool.

Run your own engine

Everything is open source. On a machine with Rust, Node 20+, Python 3.11+ and Git Bash or Linux:

git clone https://github.com/angelraph/aegis-gate
cd aegis-gate
cargo test -p aegis-core
cargo build --release -p aegis-core
# build frost-tools and zcash-devtool (patches/zcash-devtool-nu7.patch),
# put frostd, frost-client, zcash-devtool and aegis in tools/bin, then:
./apps/engine/start.sh

The start script launches the relay and engine, opens a public tunnel, and points the website at it.

Roadmap

  1. Signer in your browser. Each share stays on its owner's device. Before signing, it shows "pay X ZEC to Y" and refuses anything else.
  2. Choice of arbiter. Pick an independent arbiter per deal.
  3. First purchase as onboarding. Set up a wallet, get ZEC and shield it inside your first deal.
  4. Mainnet. Small real trades with the community, each auditable through its viewing key.
